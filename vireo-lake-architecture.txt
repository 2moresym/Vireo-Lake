==============================================================================
PART 1 - ARCHITECTURE
==============================================================================

1. GOALS AND NON-GOALS
----------------------

Goals
  - Vireo: a from-scratch, Vulkan-style explicit graphics API. Low CPU
    overhead (no OpenGL-style hidden state tracking, no per-draw driver
    work), general purpose (2D, 3D, particles, compute).                [DECIDED]
  - First target GPU: Intel HD 4000 (Ivy Bridge, Gen7, 16 EUs) on Linux.
    Machine is a low-end laptop with 4 GB RAM shared with the GPU.      [DECIDED]
  - Lake: a renderer built on top of Vireo (frame graph, 2D, 3D,
    particles). Lake is the first and main client of Vireo.            [DECIDED]
  - Reuse Vulkan DESIGN ideas (dynamic rendering, synchronization2-style
    barriers, timeline semaphores, push descriptors, pipeline cache) and
    reuse Mesa's Intel code (compiler, packet descriptions) where it is
    licence-compatible. Do NOT reimplement Vulkan extensions as such: they
    are spec text for another API.                                     [DECIDED]
  - Other architectures will be added LATER. The design must have a clean
    backend seam so a second backend does not require rewriting the core.
                                                                        [DECIDED]

Non-goals (for now)
  - Windows/macOS. Linux only.
  - Vulkan/OpenGL compatibility. (A translation layer could come much later.)
  - Mesh shaders, ray tracing, native 16-bit math (HD 4000 has none).
  - Async compute (Gen7 has a single render engine plus a blitter). [VERIFY]

3. LANGUAGE SPLIT                                                      [DECIDED]
-----------------

  C     - vireo.h (the public ABI) and the thin shim around Mesa's compiler.
          Mesa's compiler is C++, so the shim is a small C++ file exposing
          extern "C" functions.
  Zig   - Vireo core, all backends, packet packing, kernel interface.
          Everything on the hot path lives in Zig. Zig 0.16 is installed;
          the Zig std API changes between versions, so always check the
          installed version's std instead of relying on memory.
  Rust  - Lake, the validation layer, offline tools (shader precompiler,
          pipeline cache builder). Lake talks to Vireo ONLY through vireo.h,
          via a safe Rust wrapper crate ("vireo-rs").

  Cross-language rule: keep calls across the C ABI flat (no allocation, no
  callbacks in per-draw calls).


4. PUBLIC API RULES (vireo.h)
-----------------------------

  - Prefix: Vr / vr / VR_  (e.g. vrCreateBuffer, VrBuffer).             [DEFAULT]
  - Opaque handles (pointers to incomplete structs or 64-bit ids). No
    exposed backend types.
  - Flat structs with explicit sType-less, versioned layouts: every
    descriptor struct starts with a `size` or `version` field so it can grow.
  - No varargs, no C++ types, no callbacks except in explicit debug hooks.
  - Errors are return codes (VrResult). No exceptions, no hidden globals.
  - Everything explicit: the app creates and owns memory, pipelines,
    descriptor sets, command buffers, sync objects.
  - Capability model: the API has a BASELINE (everything Gen7 can do) plus
    optional features/extensions, queried at runtime via a limits struct and
    named extensions (VR_EXT_*). New hardware adds capability bits instead of
    changing the baseline.

  Core object set (first version):
    Instance, Device, Queue, Memory (allocation), Buffer, Image, ImageView,
    Sampler, ShaderModule, Pipeline (graphics, compute), DescriptorLayout,
    DescriptorSet, CommandBuffer, Fence/TimelineSemaphore, Surface/Swapchain
    (export to dma-buf; window-system glue lives in Lake or a small
    companion library).


5. VIREO CORE MODULES (Zig, backend-agnostic)
---------------------------------------------

  recorder     Command recording API. Writes through a per-backend encoder
               into a mapped batch buffer (bump pointer). No allocations per
               draw.
  pipelines    Pipeline creation: validates description, asks the shader
               compiler for machine code, asks the backend to bake ALL
               hardware state into an opaque blob. Binding a pipeline = copy
               the blob's dwords into the batch.
  descriptors  Layouts and sets. The backend decides the hardware form
               (Gen7: surface states + binding tables).
  memory       Heaps, allocations, suballocators, budget query. The core
               owns policy (pools, alignment, lifetime); the backend owns
               hardware specifics (tiling, caching modes).
  sync         Fences, timeline semaphores, barrier descriptions. Barriers
               are explicit and translated by the backend.
  caps         Device limits, feature bits, extension registry.
  debug        Object naming, debug hooks, counters.

  Hard rule: NOTHING in the core may include or assume Gen7 concepts
  (binding tables, 3DSTATE packets, i915 ioctls). If the core needs to know
  something hardware-specific, it asks through the backend interface.


6. THE BACKEND INTERFACE (the multi-architecture seam)
------------------------------------------------------

Design: a Zig struct of function pointers ("vtable") per backend, plus a
build option to compile a single backend statically with no indirection.

  - Runtime mode:  backend chosen at device creation (probe hardware, pick
    the first backend whose probe succeeds). One indirect call per recorded
    operation is acceptable.
  - Static mode:   `zig build -Dbackend=gen7` monomorphizes the core against
    one backend with comptime, so the vtable disappears from the hot path.
    Use this for release builds and benchmarks.                        [DEFAULT]

Backend responsibilities (the interface, conceptually):

  probe / open        Detect a supported device, open it, report identity.
  caps                Fill limits, features, queue families, memory heaps,
                      supported formats and tilings.
  memory              Allocate/free device memory, map/unmap, choose caching
                      mode, choose tiling for images, report image layout
                      (size, alignment, pitch).
  shaders             Declare which compiler it needs; consume compiled
                      machine code; return per-stage metadata (register
                      counts, binding usage).
  pipelines           Build a backend blob from a pipeline description plus
                      shader binaries (all hardware state pre-packed).
  descriptors         Define set layout in hardware terms; write descriptors;
                      produce bindable form.
  encoder             Record: begin/end, bind pipeline, bind descriptors,
                      bind vertex/index buffers, push constants, set dynamic
                      state, draw, draw indexed, dispatch, copy, fill,
                      clear, barrier, begin/end rendering (dynamic
                      rendering), timestamp.
  submit              Turn command buffers into a submission; relocation
                      handling; signal/wait sync objects.
  sync                Fence/timeline creation, wait, query.
  present-export      Export an image as a dma-buf for the window system.
  debug               Hang detection, error decoding, counters.

Rules:
  - The core never inspects a backend blob; it only stores and hands it back.
  - Everything the API exposes must be expressible through capability bits,
    so a weaker backend can say "not supported".
  - A "null" backend (no GPU) is mandatory: it implements the interface with
    a CPU-side recorder that only validates/logs. It lets the core, the
    validation layer, Lake and CI run without hardware.               [DEFAULT]
  - A "reference" software rasteriser backend is a possible later addition
    for correctness comparison.

Candidate future backends (informational, not planned work):
  - Other Intel generations. Mesa's older-hardware compiler ("elk") covers
    Gen4-Gen8 and the newer compiler ("brw") covers Gen9+.            [VERIFY]
  - Other vendors via their Linux kernel interfaces.


7. GEN7 BACKEND (HD 4000) - HARDWARE REALITIES
----------------------------------------------

Everything here is [VERIFY] against the Ivy Bridge PRM volumes (command
stream, 3D pipeline, EU ISA/shared functions) and against Mesa's
`hasvk`/`crocus`/`elk` sources. Never guess bit layouts.

  - Resource access is through binding tables + surface states, not bindless.
    Descriptor sets therefore compile to prebuilt surface-state and
    binding-table chunks.
  - GPU address space is about 2 GB (aliasing PPGTT). Plan on 32-bit GPU
    addresses. Softpin needs full PPGTT, which is unreliable on Ivy Bridge,
    so expect to use relocations in execbuf.
  - Queues: one render engine (3D + compute) and one blitter. Expose one
    graphics/compute queue and one transfer queue. No async compute.
  - Memory: unified with system RAM; the LLC is shared with the CPU. Offer
    cached host-visible mappings (readback) and write-combined mappings
    (uploads). Total RAM is small, so the memory budget is a first-class
    query and suballocation is mandatory.
  - Tiling: render targets and textures want X or Y tiling; scanout wants X
    tiling or linear. The BACKEND chooses tiling at image creation; the app
    does not.
  - Workarounds: Gen7 needs PIPE_CONTROL stalls/flushes around certain state
    changes. Keep them in ONE module (gen7/workarounds.zig), each entry
    commented with its PRM section or Mesa source reference.
  - Shader stages present in hardware: VS, HS, DS, GS, PS, compute. Vertex-
    side stages on this generation are compiled by the vec4 backend of
    Mesa's compiler; fragment and compute are scalar.                 [VERIFY]
  - Not exposed: mesh shaders, ray tracing, native 16-bit math.
  - Render passes buy nothing on this GPU (immediate-mode renderer). Use
    dynamic rendering: begin/end rendering with attachments given at record
    time.

Packet packing:
  - Do not hand-write every 3DSTATE_* / PIPE_CONTROL / MI_* bitfield.
    Mesa's genxml has machine-readable Gen7 packet descriptions. Write a
    small generator (Zig comptime or a script) that turns them into Zig
    `packed struct` packers plus a pack function. Keep the generated files
    checked in and note the Mesa commit they came from.


8. SHADER COMPILER STRATEGY
---------------------------

  - Vireo's shader input is SPIR-V.                                    [DEFAULT]
  - Pipeline: SPIR-V -> NIR (Mesa) -> Intel compiler (elk for Gen7) ->
    machine code + metadata. The user intends to modify Mesa's compiler for
    the HD 4000.                                                       [DECIDED]
  - Integration: a small C-ABI shim library (`vireo-shc`) wrapping the parts
    of Mesa needed. Mesa is MIT-licensed; keep headers, record provenance
    (Mesa commit) in a PROVENANCE file, keep modifications in a clearly
    marked patch series or fork.
  - Extracting the compiler from Mesa may be non-trivial (it depends on NIR
    and Mesa utility code). Expect to vendor a pinned Mesa checkout and build
    only the needed targets. Decide the exact approach in the milestone that
    introduces it, and record the decision.                            [VERIFY]
  - Early bring-up must NOT wait for the compiler: use hand-assembled EU
    code first (Mesa's tree includes an assembler and disassembler tool for
    the older-hardware compiler; verify target names).                 [VERIFY]
  - Shaders are compiled at pipeline creation; a pipeline cache (on disk)
    stores results keyed by shader hash + hardware id + compiler version.


9. KERNEL INTERFACE (Gen7 backend)
----------------------------------

  - Use the render node (/dev/dri/renderD*), not the primary node. This
    avoids display-master conflicts, so tests cannot black out the desktop by
    themselves.                                                        [DEFAULT]
  - Use the i915 uAPI directly (Zig @cImport of i915_drm.h): context create,
    GEM create/mmap/caching/tiling, execbuf2, GEM wait, syncobj for
    fences/timeline. Do not depend on libdrm's Intel buffer manager.
  - A GPU hang bans the offending context and can trigger a GPU reset that
    makes the compositor flicker. Hang handling is part of the backend:
    detect the ban/reset, mark the device lost, return VR_ERROR_DEVICE_LOST.
  - Keep the kernel interface in its own Zig module
    (backends/gen7/kernel_i915.zig) so another kernel driver could be
    substituted.


10. HOW LOW CPU OVERHEAD IS ACHIEVED
------------------------------------

  1. Pipeline objects bake ALL hardware state; binding is a memcpy.
  2. Command buffer = bump pointer into a mapped batch BO. No per-draw
     allocation, no per-draw hash lookups.
  3. No implicit hazard tracking. Barriers are explicit (synchronization2
     style); Lake's frame graph computes them once per frame.
  4. Descriptors are prebuilt hardware chunks; binding a set is pointer work.
  5. Validation is a separate layer (Rust), absent from release builds.
  6. Long-lived pooled buffers with suballocation. No create/destroy in the
     frame loop. One execbuf per queue submission.
  7. Relocation lists are reused/pre-sized; no growth on the hot path.
  8. Static-backend build removes vtable indirection (section 6).


11. LAKE (RENDERER, Rust)
-------------------------

  - Talks to Vireo only through vireo-rs (safe wrapper over vireo.h). The
    wrapper encodes lifetimes so handle misuse fails to compile.
  - Frame graph: passes declare resource reads/writes; Lake computes
    barriers, aliasing, and lifetimes once per frame, then records.
  - Renderers on top: 2D (batched quads, sprites, text), 3D (forward
    renderer first; deferred is out of scope for HD 4000), particles
    (CPU-simulated first, compute later).
  - Presentation: render to images, export as dma-buf, present through
    Wayland linux-dmabuf. Window-system code lives in Lake (or a companion
    crate), never in Vireo core.
  - Lake must run on the null backend for tests.


12. VULKAN IDEAS: BORROW vs SKIP
--------------------------------

  Borrow (as design):
    dynamic rendering; synchronization2-style barriers; timeline semaphores
    (mapped to DRM syncobj); push descriptors / descriptor-buffer style
    binding; pipeline cache; buffer-device-address-style GPU pointers
    (32-bit on Gen7).
  Skip:
    render passes/subpasses; mesh shaders; ray tracing; anything needing
    64-bit stateless addressing or 16-bit arithmetic on Gen7.

15. SAFE HARDWARE TESTING (testbox)                                    [DECIDED]
-----------------------------------

The owner does not want tests to lock them into a black desktop. Therefore:

  - All GPU tests run through `tools/testbox`, a small runner:
      * runs each test in a child process with a hard timeout (default 10 s)
        and kills it on timeout;
      * uses the render node only; never opens the primary node and never
        becomes DRM master;
      * captures the kernel log (i915 hang/reset lines) before and after
        each test and attaches the difference to the report;
      * on a detected hang or reset, stops the run, prints what happened and
        exits non-zero without running further GPU tests;
      * by default refuses to run display/presentation tests; those need an
        explicit `--display` flag and are meant to be started from a spare
        TTY. Before any display test the runner records the current VT and
        restores it on exit (including on failure).
  - Never run experimental GPU code outside testbox.
  - The null backend must let most work proceed with no GPU risk at all.


16. KNOWN RISKS AND OPEN QUESTIONS
----------------------------------

  - Extracting Mesa's compiler into a standalone shim may be heavy.
  - Ivy Bridge quirks (PPGTT, workarounds) can cost a lot of debugging time.
  - Zig 0.16 std API differences from older docs and examples.
  - Keeping Vireo's baseline honest: the baseline must not silently assume
    Gen7-only behaviour, or the second backend will hurt.
  - Wayland presentation details (modifiers, sync) are not designed here.
